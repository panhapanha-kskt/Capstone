D · What this means for the model

  • Feature engineering: 'entropy' alone nearly separates the classes. High model scores will mostly reflect this one measure; add harder data (long benign names, short-name attacks) before trusting accuracy.
  • Bias: attack and benign data come from different periods. Keep time fields (timestamp, hour, day) out of the features, and test on data captured in the same period.
  • Feature engineering: labeled rows have no response codes / answers (PCAP queries only) while Technitium logs do. Don't rely on answer_count or RCODE features until both sources record them.
  • Feature engineering: 2026-03-18.log is one client producing mostly NXDOMAIN. Per-query features can't see that; per-client behavioural features (NXDOMAIN share, query rate, unique subdomains per parent) would.
  • Algorithm choice: length/count measures are strongly right-skewed with long tails. Tree models (Random Forest, Gradient Boosting) handle this without scaling; linear or distance-based models would need log scaling.
  • Algorithm choice: labeled class ratio is 1.2:1 — balanced enough; report PR-AUC alongside F1.
  • Garbage in: unlabeled rows will get heuristic labels from the same features the model learns. Add data/attack_manifest.csv for independent labels.
