# Week 8 project audit and limitations

**DNS Traffic Anomaly Detection · reviewed 2026-11-23**

This audit records the current limitations of the project and the evidence behind them. It builds on the [Week 7 training audit](../Week7/AUDIT_TRAIN_PIPELINE_2026-11-21.md), the [project review](../Week7/PROJECT_REVIEW_2026-11-21.md), the [model card](../../models/MODEL_CARD.md), and the current source tree. The accompanying [Week 8 interface plan](WEB_INTERFACE_PLAN.md) covers the next authorized development scope.

## Scope and verification

The review covered the DNS parsing, training, scoring, promotion, monitoring, SOC server, training console, eight SOC pages, and the reports cited above. The previous interface change passed 56 dashboard regression tests and headless Chrome checks on eight SOC pages with local demo fixtures. Those checks exercised navigation, the Alerts assignment filter, Triage queue recovery, and case opening. They did not exercise live Technitium ingestion or Elasticsearch/Kibana delivery. The 16 artifacts listed in `models/PROMOTED.json` matched their recorded SHA-256 hashes during the review.

Severity describes the effect if a finding occurs. A documented design choice is identified separately from a defect. The numbers below are tied to the checked-in artifacts and should be updated after new evaluation runs.

## Findings

| ID | Severity | Finding and evidence | Consequence | Status |
|---|---|---|---|---|
| A1 | Critical | Analyst identity is supplied by the browser. [`_actor`](../../dashboard/server.py#L1480) checks only that the ID exists in `analysts.json`; [`authorize`](../../dashboard/server.py#L1499) trusts the selected ID's tier. The live `/api/analysts` response lists Tier 1, Tier 2, and Tier 3 identities and reports `authenticated: false`. | Anyone who can use the dashboard can claim a higher-tier identity. Attribution and four-eyes approval are workflow demonstrations, not authenticated controls. | Open. Require server-authenticated identities before exposing the dashboard to other users. |
| A2 | High | `scripts/train_models.sh` builds `feature_snapshot` from the first 12 numeric fields of all labeled rows. `monitor.py` checks `FEATURES_8` against that snapshot. The promoted metadata has only one matching name, `query_length`. The saved monitoring report contains only that feature, PSI 8.027, and recommends retraining. | The drift and retraining signal is unreliable. The baseline mixes benign and attack traffic and includes fields outside the model feature contract. | Open. See Week 7 audit §1. |
| A3 | High | The promoted model card reports fusion recall 1.000 and 7 false alarms among 1,168 benign test queries, a 0.60% false-positive rate. The project target is 0.10%. `config/success_criteria.yaml` judges fusion candidates, while its current-model comparison is Path A level. | The promoted operating point misses the stated budget. The gate's current-versus-candidate result is not a direct fusion-versus-fusion comparison. | Open. The rule baseline and additional data evaluation remain important. |
| A4 | High | `splits.py::_time_split` and `dns_parser.py::load_multifeature_with_meta` call `pd.to_datetime(..., errors="coerce")` without mixed-format parsing. The Week 7 audit reproduced mis-ordering with timestamps that differ in fractional seconds. | Future merged sources can be ordered incorrectly in a time split and in Path B client windows. | Open. See Week 7 audit §2. |
| A5 | Medium | `path_b_predict.py::score_records` writes scores to `last_idx`, the final query of each full 20-query window. | Early queries and clients with fewer than 20 queries lack Path B scores. This is a coverage limitation, and a scoring change would require fusion retraining and evaluation. | Open. See Week 7 audit §3. |
| A6 | Medium | `train_models.sh` registers input files during conversion and merge before all training stages complete. | A failed run can leave the registry claiming that inputs were trained, affecting later incremental retraining. | Open. See Week 7 audit §4. |
| A7 | Medium | The Week 7 audit found an in-sample fusion threshold and a gate that compares candidate fusion with current Path A. | Reported candidate gains can be biased or difficult to interpret. | Open. See Week 7 audit §5. |
| A8 | Medium | The Week 7 checklist marks dashboard testing in real mode as unfinished. The available browser checks used demo fixtures, and the Week 7 scratch live check used a temporary VM copy and stand-ins for training and the gate. | The complete browser-to-live-service workflow and Elasticsearch/Kibana export remain unverified on the intended deployment. | Open. |
| A9 | Low | `README.md` describes the autoencoder as the default Path B algorithm. `train_models.sh` currently sets `PATH_B_TYPE="iforest"`. | The quick-start explanation can lead readers to expect the wrong model. | Open documentation correction. |
| A10 | Critical | The single-alert verdict path passes the request body to [`_apply_one_inner`](../../dashboard/server.py#L480), which exempts a High/Critical false-positive verdict from Tier 2 review when client-supplied `_approved_by` is truthy. The server does not verify that value against a real approval record. | A direct request can forge an approval and write a false-positive training label. This is a separate defect from A1's identity spoofing. | Open. Reject client-supplied approval metadata; derive it only from a server-stored, independently approved close request. |
| A11 | High | [`triage_action`](../../dashboard/server.py#L2336) requires manual checklist items and a Tier 2 approval request for a Tier 1 High/Critical false-positive case closure. The individual [`status` action](../../dashboard/server.py#L423) and [`bulk` action](../../dashboard/server.py#L3157) use different paths. `--require-verdict` defaults to false. | Tier 1 can close an alert through the Alerts/API status path without the case checklist or a verdict; the case workflow is not a universal policy. | Open. Enforce one closure policy at the server layer for case, single-alert, and bulk routes; test each route. |
| A12 | High | [`ADMIN_TOKEN`](../../dashboard/training-gui/core/settings.py#L28) defaults to `admin`. A read-only request to the running demo's `/training/api/config` accepted that default. The training console can start runs and manage model promotion independently of analyst tiers. | A known token is sufficient for model-administration access in the current local demo. Broader exposure would make this a serious control failure. | Open. Require a non-default secret for the training API and separate model administration from analyst workflow permissions. |
| A13 | Medium | [`record_incident_action`](../../dashboard/server.py#L700) records `SIMULATED` or `NOT_CONFIGURED`, including firewall-block and endpoint-isolation requests. The live Elasticsearch, syslog CEF, webhook, VirusTotal, and AbuseIPDB integrations were all disabled at audit time. | Incident actions do not block an IP or isolate a host; outbound alert delivery and online enrichment were not demonstrated in this run. | By design but incomplete. Keep simulation labels visible; implement and verify each real integration separately before claiming response capability. |
| A14 | Medium | [`/api/devices`](../../dashboard/server.py#L2817) explicitly says it has no agent inventory. It derives DNS client IPs and pipeline `source_file` values; [`/api/health`](../../dashboard/server.py#L2828) covers pipeline health. | Windows, macOS, and Ubuntu connectivity, last check-in, CPU, memory, disk, OS, and services cannot be inferred from this telemetry. | Open integration gap. Add an authenticated manager-side agent feed, timestamped per metric; show unknown or stale when absent. |
| A15 | Medium | [`/api/events`](../../dashboard/server.py#L3081) filters the same detection alerts, not a general event store. [`/api/alerts`](../../dashboard/server.py#L3046) returns the newest `FEED_LIMIT=150` alerts; run history is capped at 120 in-memory points. | The interface cannot provide complete raw-event investigation, durable search, or historical case reconstruction from these APIs alone. | Open data-scope limitation. Define durable event/case retention and label the existing views accurately. |
| A16 | High | [`/api/run`](../../dashboard/server.py#L3025) checks a rate gate and records an actor but does not call `authorize`. The required `X-SOC-Request` header is a cross-site request guard, not a user permission. | A client that can reach the dashboard can request a pipeline run regardless of analyst tier. | Open. Gate manual runs with authenticated operator permission and preserve rate limiting. |

## SOC tier scope and live evidence

The platform is **Tier 1-centered, not Tier 1-only**. `/triage` provides the Tier 1 case workbench. [`PERMISSIONS`](../../dashboard/server.py#L224) and [`allowed_actions`](../../dashboard/server.py#L2177) add Tier 2 approval, suppression, escalated-case ownership, and incident-action paths. A Tier 3 analyst record exists, but no permission requires Tier 3 specifically. The training console uses its own admin token rather than an analyst tier. These labels do not establish access control until A1, A10, and A11 are fixed.

Read-only checks of `http://127.0.0.1:9000` on 2026-11-23 found the server listening on `127.0.0.1` and running in **demo** mode. The SOC pages and read-only APIs returned HTTP 200; the Tier 1 case view offered claim/checklist/close/escalate, while the Tier 2 view also offered suppress. The demo's synthetic alert count and SLA breaches grow while it runs and are not production SOC performance evidence. The training API rejected a missing token and accepted its default token. No state-changing bypass request was executed against the live records; A10, A11, and A16 are confirmed by the server control paths.

The server already sends a CSP, frame protection, no-sniff header, and host/origin checks. These reduce browser attack surface but do not authenticate an analyst or validate a four-eyes approval.

## Interface findings and current state

The earlier interface review found duplicate navigation across SOC pages, missing links to Triage from three pages, placeholder navigation items, limited narrow-screen support, and silent Triage queue polling failures. The current working tree includes a shared navigation shell, mobile menu, status display, Alerts assignment filter, and visible Triage retry flow in `dashboard/static/js/chrome.js`, `dashboard/static/css/shell.css`, `dashboard/alerts.html`, and `dashboard/static/js/triage.js`. These changes passed the checks described above. They are still working-tree changes at the time of this document and should be reviewed together with the Week 8 plan.

The remaining interface work is to verify these pages against a real-mode dashboard, improve keyboard and screen-reader behavior in the data-heavy views, and make error and freshness states consistent across pages. Those items are specified in [WEB_INTERFACE_PLAN.md](WEB_INTERFACE_PLAN.md).

## Evidence boundaries

The frozen test result comes from the promoted model card. Some Week 7 notes cite eight false alarms for a different evaluation context. Keep the dataset, run, and denominator beside each metric. The saved monitoring report is evidence of the current drift output, not proof that live traffic has drifted. The demo browser checks establish interface behavior with fixtures; they do not establish live data correctness.
